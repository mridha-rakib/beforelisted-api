# Secondary-copy outbox operation and integration

The shared `EmailService.sendEmail` path snapshots each eligible non-CRM agent secondary address in an encrypted intent before sending the primary. A confirmed primary response promotes the intent to `ready`; failed, suppressed or ambiguous outcomes remain reviewable. A crash after primary acceptance and before promotion leaves `waiting_primary`, which requires operator reconciliation. Failure to prepare an intent fails the email before provider dispatch. The existing primary transporter retry policy is unchanged and can itself have ambiguous results.

The scheduled outbox job runs on startup and every ten seconds when scheduled jobs are enabled. It claims only never-attempted ready records with majority write concern. Accepted, failed, uncertain, suppressed, pending and review records are not automatically resent. External delivery is not exactly once: a crash or write failure after provider acceptance leaves a pending record for reconciliation. To review, inspect record ID, agent ID, template, state, timestamps, attempt count and provider message ID; do not expose encrypted payloads or raw provider responses. Check provider records using approved operator access before taking any manual action. No manual resend is implemented.

Provide `SECONDARY_COPY_KEYS` as a JSON object mapping key versions to base64-encoded 32-byte AES keys; `SECONDARY_COPY_ACTIVE_KEY_VERSION` selects a version. Provide a separate stable base64-encoded 32-byte `SECONDARY_COPY_IDENTITY_KEY` for event identity and `SECONDARY_COPY_RETENTION_HOURS` (positive, at most 8760). Use a secrets manager and restricted database access. Retention erases encrypted payloads after the configured period while preserving delivery metadata; unattempted expired records become review records. Run the scheduled job for retention and recovery. Verify keys and retention are configured before enabling the feature.

For rotation, add a new version to the keyring before selecting it as active. Retain old versions until their records no longer need decryption, and verify the worker can process old and new versions. Keep the separate identity key stable across encryption-key rotations: changing it breaks duplicate recognition. Identity-key rotation needs a migration design and is not implemented.

Every invocation of the primary email pipeline generates a new dispatch identity. Existing business-event hints (`new-request`, `agent-deleted` and `renter-registration-verified`) remain attached to the identity, but do not suppress a copy when the primary is sent again. A stored intent has one database-enforced identity per dispatch, template and agent; retries or concurrent claims of that intent cannot automatically send it twice. This is delivery-level idempotency, not business-event idempotency. See `secondary-copy-event-inventory.md` for the 47 call sites and coverage limits.

The primary transporter retains its existing retries. If a provider timeout was actually accepted and a later primary attempt is also accepted, one pipeline invocation can produce multiple primary deliveries but only one secondary intent. The operator must reconcile ambiguous outcomes; the system cannot establish exact parity in this case without a change to primary retry semantics or provider-supported idempotency. Likewise, waiting-primary and pending records must be reviewed after interruptions.

The recipient resolver covers agent recipients in To, CC and BCC and preserves separate copies for each agent. CRM-only secondary settings are excluded. Agent deletion passes the saved address and ID after profile removal. The scheduled process and all nodes need the same identity key and active keyring. Deployment requires an operational owner for review states and alerts, a retention policy, and key management. No automatic resend policy is introduced.
